### Secrets and where they live

* Function secrets (set via `supabase secrets set`): `SENTINEL_KEY`,

### LEGAL — do not "simplify" these away

* **Never make it delete CSAM on sight.** 18 U.S.C. § 2258A: report to NCMEC,
  then preserve 90 days. The system quarantines to `quarantine/<sha256>` in R2
  (unreachable because `serve()` rejects any key containing `/`) and sets
  `moderation_evidence.preserved_until = now() + 90 days`, with a trigger that
  refuses early deletion.
* **Never put imagery in a report/email/notification.** Ids, hashes, counts only.
* **NCMEC filing is still manual.** The user must register as an ESP at
  <https://report.cybertip.org/espregistration>. Until then someone reviews
  `moderation_evidence where reported_at is null` and files by hand.

### The false-positive lesson — do not regress this

The first dry run over real data produced six `block`-severity text hits.
**Five were false positives, and they were people reporting abuse**: "they have
a child porn channel", "sites on the dark web often advertise child
pornography", "...server that was soliciting child pornography, rape, gore and
incest" (a note about the user's own takedown), plus a crude insult matched
twice. Going live as written would have **banned the reporters**.

Consequences now baked in, keep them:
* **Text never suspends an account.** Every rule has `suspend: false`.
  Suspension requires media evidence (hash match or classifier verdict on an
  actual image).
* A `DISCUSSING` regex demotes `block` → `review` when the text reads as
  reporting/warning/rules/news.
* Those five real strings are regression tests in `rules_test.ts`.
  **Run `deno test supabase/functions/content-sentinel/rules_test.ts` after any
  rules change.** All 4 tests must pass.
* **Always dry-run first** (`{"dryRun":true}`) before enabling anything new.

## 5. How to operate the scanner

```bash
URL=https://mjqbrcabargylrimlafw.supabase.co/functions/v1/content-sentinel

# Report-only; changes nothing.
curl -X POST "$URL" -H "Authorization: Bearer $SENTINEL_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"mode":"text","dryRun":true,"full":true,"maxRows":6000}'
```

A **full backfill exceeds one invocation's CPU budget** — drive it in chunks:
each response returns `nextOffset`; feed it back until `null`. ~6,000 text rows
per call is safe. Media: `{"mode":"media","limit":250}`, about 0.5 s per file,
~6,800 files total, so a full media backfill is ~28 runs.

Useful SQL:
```sql
select * from public.content_flags where state='open' order by created_at desc;
select * from public.moderation_actions order by created_at desc limit 50;
select * from public.safety_runs order by started_at desc limit 10;
select id, sha256, category, preserved_until
  from public.moderation_evidence where reported_at is null;
```

## 6. Hard-won gotchas — these all cost real time

1. **Supabase `apply_migration` can silently skip a statement.** A
   `drop index` reported success and did nothing. **Always verify with a
   follow-up query** that the object exists / is gone.
2. **The `mcp__supabase__*` tools lack permission on this project.** Use the
   other Supabase MCP server (id beginning `f6a2cde0…`) — it works.
3. **PostgREST caps responses at 1,000 rows.** Asking for 5,000 and treating a
   short page as "done" stopped the first sweep after 1,000 of 75,000 rows.
   Advance by `rows.length`, never by the requested page size.
4. **Edge functions have a hard CPU/memory ceiling** (HTTP 546 /
   `WORKER_RESOURCE_LIMIT`). Fetching rows with megabyte-sized message bodies
   blew it — hence `left(col, 4000)` in the view and a 4,000-char cap in
   `scanText`. Chunk long jobs.
5. **Always pass `-c wrangler.toml` when working in `cloudflare/cdn-worker`.**
   Otherwise wrangler walks up and uses the repo-root `wrangler.jsonc` (the
   Next-on-Workers config, name `disband`) — that is how the stray Worker and
   the misplaced secret happened.
6. **`serve()` in the CDN worker rejects any key containing `/`.** That is what
   makes `quarantine/<sha>` unreachable; don't "fix" it.
7. **The auto-mode classifier blocks production writes from Bash** (Supabase
   REST writes via curl) and blocks printing credentials. Use the Supabase MCP
   for DB writes; for secrets, design so the secret never has to be read (the
   Vault + `sentinel_check_key` pattern).
8. **The app is login-gated and you must never enter the user's credentials.**
   The iPhone 17 Pro simulator is already signed in — use it for verification;
   don't erase it.
9. **Don't take actions that reach real users to get a screenshot** — joining
   voice writes presence, starting a group call rings people and sends pushes.
10. **iOS previews**: Next.js treats `_`-prefixed route folders as private, and
    Xcode/XcodeGen needs `xcodegen generate` after adding files.

## 7. How the user expects you to work

* **Verify, then claim.** Build it, run it, screenshot it, query the database.
  Don't report success from having written code.
* **Dry-run anything that removes content or bans accounts**, and read the
  sample before going live.
* Say plainly what you did **not** do or could not verify. The user is fine
  with blockers; they are not fine with silent gaps.
* Match the surrounding code's comment density and voice: comments explain
  **why**, especially where a non-obvious decision prevents a specific bug.
