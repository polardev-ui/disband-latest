Security & RLS

Clients hold a real Postgres session. Row Level Security, not the interface, decides what they can do.

The UI is not a security control. Hiding a button stops an ordinary user from stumbling into an action. It stops nobody from calling the API directly. Every rule that matters must exist as an RLS policy or inside a security definer function.

Permissions

Server permissions resolve through member_has_server_permission(server_id, user_id, permission). It:

  1. Refuses to answer for anyone but the caller, so it cannot be used to probe other users' permissions.
  2. Returns true immediately if the user owns the server — owners implicitly hold every permission.
  3. Otherwise resolves the member's roles and checks the permission flag.
PermissionGrants
manage_channelsCreate, rename, reorder and delete channels and categories; post in announcement channels.
manage_rolesCreate and assign roles.
manage_serverEdit server settings.
manage_messagesDelete other people's messages.
kick / banRemove or ban members.
manage_emojisManage custom emoji.
mention_everyoneUse @everyone and @here.

Worked example: announcement channels

Marking a channel read_only hides the composer. That alone would be trivial to bypass, so the rule lives in the insert policy:

create policy "messages_insert" on public.messages for insert to authenticated
  with check (
    auth.uid() = author_id
    and exists (
      select 1 from public.channels c
      where c.id = messages.channel_id
        and public.is_server_member(c.server_id)
        and (
          c.read_only = false
          or public.member_has_server_permission(
               c.server_id, auth.uid(), 'manage_channels')
        )
    )
  );

Postgres combines multiple permissive policies with OR. Adding a second policy to "tighten" a rule does the opposite — it widens access. To restrict, rewrite the existing policy or add a restrictive one.

Privileged functions

Operations that need to read beyond the caller's own rows run as security definer with a pinned search_path. They must guard their own inputs, because RLS no longer protects them. Examples include get_or_create_dm_thread, join_server_by_invite and list_discoverable_servers.

Some columns are protected by triggers rather than policies: the badge flags on profiles are reset to their previous values on update, so a user cannot grant themselves a staff badge by writing to their own row.

Keys

KeyWhere it may be used
Anon keyClient-side. Safe to ship — it grants nothing on its own, since RLS still applies.
