Building a bot Planned

Disband bots are self-hosted. You run the bot yourself, and a server owner invites it — the same way they invite a person.

This is not built yet. As of v1.0.26 there are no bot accounts, no bot tokens, no invite flow and no gateway. Nothing in the codebase implements them. This page is the intended design, written down so it can be reviewed and built — not an API you can call today.

The model

StepWhat happens
1. CreateA developer registers a bot in Disband and receives a bot token. The token identifies the bot; it is not tied to a human account.
2. Self-hostThe developer runs the bot on their own machine or server. Disband does not host or execute bot code.
3. InviteA server owner opens the bot's invite link, sees the permissions it is asking for, and approves. The bot joins as a member.
4. OperateThe bot connects to Disband with its token and acts only inside servers it was invited to, limited by the roles it was given.

Why self-hosted

Running bot code on Disband's infrastructure would mean executing untrusted programs next to user data. Self-hosting keeps that boundary clean: a bot is just a client holding a token, subject to the same permission checks as anyone else.

Credentials

Bot developers never receive database credentials. A bot authenticates with its own token against Disband's API. It does not get Supabase project details, and it does not talk to Postgres directly. That boundary is the whole point — it means a bot's reach is defined by the permissions a server owner granted, and can be revoked by removing the bot.

Worth being precise about one thing: the anon key shipped in Disband's own web and mobile clients is public by design — it is embedded in every build and grants nothing on its own, because Row Level Security decides what any request can actually read or write. It is not a secret, but it is also not a bot credential, and building an integration on it is not the supported path. See Security & RLS.

The service role key is a different matter entirely. It bypasses RLS and grants full read and write access to every account and message on the instance. It must never be given to a bot, committed, or shipped to any client.

Proposed shape

Everything below is illustrative. These endpoints do not exist.

Authenticating

Authorization: Bot <your-bot-token>

Receiving events

// Illustrative only.
import { Client } from "@disband/bot";           // not published

const client = new Client({ token: process.env.DISBAND_BOT_TOKEN });

client.on("messageCreate", async (message) => {
  if (message.author.bot) return;
  if (message.content !== "!ping") return;
  await message.reply("pong");
});

await client.connect();

Sending a message

POST /api/v1/channels/:channelId/messages
Authorization: Bot <token>
Content-Type: application/json

{ "content": "Deploy finished", "reply_to_id": null }

Permissions

A bot's invite link declares the scopes it wants. The effective permission is the intersection of its requested scopes and the roles it holds in that server — a bot can never exceed what its roles allow.

ScopeAllows
messages.readReceive messages in channels it can see.
messages.writePost and reply.
members.readRead the member list.
channels.manageCreate and edit channels.

What still has to be designed

  • Token issuance, rotation and revocation, and what a leaked token exposes.
  • Whether events arrive over a persistent gateway or webhooks.
  • How bots appear in the UI — a BOT tag, and a members-list grouping.
  • Slash command registration and dispatch.
  • Rate limits, per token and per server.
  • Audit and removal: a server owner must be able to see what a bot did and revoke it in one action.

Want to help build it? The honest starting point is schema and RLS — a bot identity that sidesteps the permission model would be worse than having no bot API at all. See Contributing.
