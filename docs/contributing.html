Contributing

Conventions that matter in this codebase, mostly learned the hard way.

Before you start

  • Work on a branch and open a pull request into main.
  • Run pnpm build and the TypeScript check before pushing.
  • Match the surrounding code — naming, comment density and structure vary by area; follow the file you are in.

Database changes

  • Add a new numbered file in supabase/migrations/. Never edit an applied migration.
  • Make migrations idempotent: if not exists, create or replace, drop policy if exists.
  • Enable RLS on every new table and write policies in the same migration. A table without policies is either invisible or wide open.
  • To tighten an existing rule, rewrite the policy. Adding another permissive policy widens access, because Postgres ORs them.

Security

  • Enforce authorization in RLS or a security definer function. Treat client-side checks as cosmetic.
  • Guard the inputs of security definer functions — RLS no longer protects them.
  • Keep SUPABASE_SERVICE_ROLE_KEY server-side, always.

iOS

  • Run xcodegen generate after adding or removing files; the .xcodeproj is generated and not committed.
  • Retain RealtimeSubscription tokens returned by onBroadcast and onPostgresChange. Dropping one silently unregisters the callback.
  • Prefer .task(id:) over withObservationTracking for lifecycle work. The latter fires once and re-registers asynchronously, so changes in the gap are lost.

Realtime

  • Set ack: true and check for "ok" before unsubscribing after a broadcast.
  • Design signalling so crossed messages are survivable — treat cancel and leave as equivalent rather than binding each to one state.

Verifying

Prefer evidence over inference. When a change is visible, run the app and look at it; when it is a data change, query the database. Several bugs in this codebase looked like network problems and turned out to be a discarded callback token or a state flag reused for two meanings — reading the code alone would not have settled it.

Documentation

These pages are static HTML in disband-docs/, with no build step. Edit a file, open it in a browser. If you document something that is not built, label it Planned and say so plainly — docs that describe imaginary features cost developers more time than missing docs.
